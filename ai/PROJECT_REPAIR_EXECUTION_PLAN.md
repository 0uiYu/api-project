# API 中转站项目修复执行计划

## 总原则

1. 先确认数据模型和现有业务，不用前端显示推断后端行为。
2. 每个阶段先读调用链，再修改代码，再做针对性验证。
3. 不把“菜单隐藏”当成权限控制，不把“接口能返回”当成业务完成。
4. 所有统计都标明数据来源和统计口径。
5. 计费相关修改必须检查预扣、结算、退款和日志四个阶段。
6. 数据库变更必须考虑 SQLite、MySQL、PostgreSQL。
7. 未完成真实外部平台协议核对前，不宣称已兼容连动店铺。

## 阶段 0：建立基线

目标：固定当前代码状态，确认当前问题可重复。

检查内容：

- 工作区状态和当前提交；
- 前端 TypeScript、lint、测试入口；
- 后端编译和已有测试入口；
- 路由是否能启动；
- 当前中文语言包是否有效；
- 管理员摘要、渠道状态、兑换码 webhook 的现状。

验收：记录所有可复现错误；不修改业务逻辑。

## 阶段 1：修复统计数据模型错误

目标：修复管理员用户摘要和运营统计的字段、口径、权限。

工作：

- `TopUp` 统计区分订单数、支付金额、到账额度；
- 只统计成功订单的到账额度；
- 检查 `Log` 的消费记录和失败记录口径；
- 失败请求不能简单等同于“总请求减成功请求”，除非代码确实有统一请求日志；
- 接口错误时前端不得把错误或未加载状态显示成 0；
- 管理员接口必须经过 `AdminAuth` 和对应权限。

验收：用 SQLite 测试数据验证成功充值、失败充值、消费日志和空数据。

## 阶段 2：重做兑换码订单流程

目标：建立可幂等、可追踪、不会重复发码的订单流程。

工作：

- 先确认连动店铺真实回调字段、签名和重试协议；
- 本地商品 ID 映射到本地额度，不信任外部直接传入 quota；
- 订单状态扩展为 pending、processing、delivered、failed；
- 使用数据库锁或原子状态更新阻止并发重复发送；
- 保存 provider order ID、商品 ID、用户邮箱、兑换码 ID、发送次数、失败原因；
- webhook 重试时返回稳定结果；
- 邮件发送失败时允许管理员重试；
- 兑换码仍然只能通过原有单次兑换逻辑使用。

验收：重复回调、并发回调、错误签名、未知商品、邮件失败、已发送订单重试。

## 阶段 3：核对用户、Token、用户组、渠道组

目标：明确“用户选择渠道”在业务上到底代表什么。

工作：

- 梳理用户组、Token 组、渠道组和 Ability 的实际关系；
- 决定前台选择是 Token 固定绑定、请求级过滤还是展示选项；
- 如果只是用户选择线路，增加安全的 Token/线路约束字段；
- 后端渠道选择器必须真正使用该约束；
- 防止用户通过请求参数绕过渠道权限；
- 模型广场只展示用户有权使用且确实有 Ability 的模型。

验收：不同用户组、不同 Token 组、不同渠道状态下，请求命中结果符合预期。

## 阶段 4：统一模型广场和价格定义

目标：分离官方参考价格、平台销售价格、上游成本和实际扣费。

工作：

- 设计稳定的前台模型 DTO；
- 明确供应商/渠道名称与后端渠道组的区别；
- 展示输入、输出、缓存读、缓存写价格；
- 标记价格来源和更新时间；
- 不向普通用户泄露上游 Key、内部余额、真实成本和敏感备注；
- 中文、英文和图标都从统一数据源读取；
- 菜单和模型广场所有文本走 i18n。

验收：前台展示价格与一次真实请求的结算日志可追溯对应。

## 阶段 5：验证计费和日志

目标：确保展示价格、实际扣费、日志快照一致。

工作：

- 追踪文本、WebSocket、音频、图片、工具调用四条计费路径；
- 验证输入、输出、缓存读取、缓存写入不重复计费；
- 验证钱包、Token、订阅预扣和退款；
- 验证失败请求不会错误扣费；
- 日志保存请求时的倍率快照和价格快照；
- 官方成本不可得时显示“不可用”，不伪造利润。

验收：固定 usage 输入下，预期额度、用户扣费和日志数值一致。

## 阶段 6：权限和管理端菜单

目标：实现前端显示与后端权限一致。

工作：

- 普通用户、管理员、超级管理员分别验证菜单；
- 所有管理 API 验证 AdminAuth/RootAuth/Casbin；
- 菜单标题、页面标题、按钮、错误提示全部检查中英文语言包；
- 语言切换后不需要重新登录；
- 不能把无权限、加载失败、空数据显示成成功或 0。

验收：三种角色逐项访问页面和 API，记录 401/403/200 结果。

## 阶段 7：数据库和发布验证

目标：确保修改能在实际部署方式下运行。

工作：

- SQLite 迁移和测试；
- MySQL 迁移和测试；
- PostgreSQL 迁移和测试；
- 前端构建；
- 后端构建；
- Docker Compose 开发环境验证；
- 生产嵌入前端构建验证；
- 最后再提交和推送。

验收：所有未完成项明确记录，不以“编译通过”代替业务验证。

## 执行顺序

严格按：阶段 0 → 阶段 1 → 阶段 2 → 阶段 3 → 阶段 4 → 阶段 5 → 阶段 6 → 阶段 7。
