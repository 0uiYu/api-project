# API 中转站管理端审计报告

## 1. 审计范围

本次审计覆盖：

- Go 网关入口、路由、中间件、控制器、服务层、模型层和 relay 层；
- React 前端路由、功能模块、管理员侧边栏、权限过滤、Dashboard、渠道、模型、用户、API Key、日志、兑换码和订阅页面；
- 当前工作区中已有的用户端模型广场、价格展示、官方参考价格和渠道状态改造。

本报告描述当前代码真实实现，不把目标功能当成已实现功能。

## 2. 当前架构

```text
浏览器 / OpenAI-compatible client
        │
        ├── React + TanStack Router/Query/Table + Zustand
        │       └── web/src/routes、web/src/features
        │
        └── Go Gin API
                ├── middleware：认证、限流、请求上下文、审计
                ├── router：接口分组和权限入口
                ├── controller：HTTP 参数处理和响应
                ├── service：业务、计费、支付、任务
                ├── model：GORM 数据模型和查询
                ├── relay：协议转换、渠道选择、上游请求
                └── Redis/主数据库/日志数据库
```

技术栈：

- 后端：Go、Gin、GORM；
- 前端：React、TypeScript、Rsbuild、TanStack Router/Query/Table；
- 主数据库：SQLite、MySQL、PostgreSQL；
- 日志数据库：可使用独立日志数据库，部分场景支持 ClickHouse；
- 缓存：Redis 和内存缓存。

## 3. API 请求真实链路

当前中转请求的业务链路由认证、relay、渠道缓存、计费和日志共同完成：

```text
客户端请求
→ API Key/Token 鉴权
→ 用户和 Token 状态校验
→ 请求模型解析
→ 用户组、Token 组和自动组规则处理
→ 查询支持该模型的候选渠道
→ 过滤渠道状态、协议、请求路径和其他约束
→ 按优先级、权重和重试规则选择渠道
→ 模型映射和协议转换
→ 请求上游
→ 解析上游响应、Token 和任务用量
→ 预扣、结算或退款
→ 写入消费日志
→ 更新统计数据和渠道使用数据
→ 返回客户端
```

实际请求使用的是 `Channel`，不是前端展示用的 Vendor 元数据。

## 4. 核心数据模型

### Channel

渠道记录保存实际上游请求所需信息，包括：

- 类型；
- 名称；
- Base URL；
- 密钥；
- 支持模型字符串；
- 模型映射；
- 分组；
- 优先级；
- 权重；
- 启用或禁用状态；
- 测试时间和响应时间；
- 使用额度和渠道附加配置。

渠道状态会影响实际路由，不是纯展示字段。

### Model / Model Metadata / Pricing

项目同时存在运行时价格、模型元数据和模型展示价格相关结构。

当前工作区已经增加官方参考价格字段：

- 输入价格；
- 输出价格；
- 缓存读取价格；
- 缓存创建价格。

这些字段已接入结算日志的参考成本计算；只有输入、输出及缓存价格完整时才记录参考成本。它们仍不是供应商账单成本。

### User / Token

- User 保存角色、余额、用户组、邀请关系和账户状态；
- Token 保存 API Key、所属用户、额度、状态、过期时间、IP 限制、模型限制、分组和自动组等；
- 浏览器登录会话和 API Key 是两套不同的访问凭证。

### Log / QuotaData

调用日志保存单次请求信息，包括用户、模型、渠道、Token、额度、耗时、请求 ID 和上游请求 ID等。

`quota_data` 是按小时聚合的统计数据，主要字段包括：

```text
user_id、username、model_name、created_at、use_group、token_id、channel_id、node_name、token_used、count、quota
```

当前模型调用分析读取的是 `quota_data`，不是逐条实时调用日志。

## 7. 模型调用分析真实含义

当前顶部统计卡片：

- `Total Count`：`quota_data.count` 的总和，表示聚合后的调用次数；
- `Total Quota`：`quota_data.quota` 的总和，表示用户侧扣除的内部额度，不等于上游成本或利润；
- `Total Tokens`：当前写入统计的是输入 Token 加输出 Token；
- `Average RPM`：查询区间内总请求数除以总分钟数；
- `Average TPM`：查询区间内总 Token 除以总分钟数。

当前消费日志已独立持久化输入、输出、缓存读取和缓存创建 Token；旧统计数据仍可能没有这些字段，因此前端对历史记录兼容为空。

管理员访问 `/api/data`，普通用户访问 `/api/data/self`。管理员默认查看全站聚合数据。

性能健康区域使用独立的性能指标接口，默认窗口是最近 24 小时，不能直接认为它和当前筛选时间范围完全一致。

## 8. 兑换码和邀请现状

当前项目已有预生成兑换码及兑换逻辑，兑换时会校验状态、有效期和重复使用，并增加用户额度。

当前已实现供应商无关的外部店铺回调、HMAC 验签、订单幂等、兑换码生成、SMTP 发货和失败重试；具体第三方店铺仍需按项目定义的回调协议适配。

当前已有邀请关系字段和邀请相关接口，但需要继续核实奖励触发条件。默认配置中的邀请奖励可能为零，因此不能直接宣称系统已经支持充值返佣或消费返佣。

## 9. 当前与目标 API 中转站的差距

### 已具备基础能力

- 多上游渠道配置；
- 渠道支持模型和模型映射；
- 渠道状态、优先级和权重参与路由；
- API Key 鉴权；
- 用户额度和模型计费；
- 调用日志；
- 聚合统计；
- 兑换码基础能力；
- 订阅和支付相关模块；
- 管理员和普通用户权限基础。

### 仍需整理或补强

- 管理端菜单需要完全围绕 API 中转运营；
- 渠道状态需要与实际路由状态保持一致并补充运营指标；
- 模型用户价格、参考成本和参考利润已拆分；真实供应商成本仍需外部账单数据；
- 新消费日志已保存结算时的价格倍率快照，旧日志没有这些字段；
- 新消费日志已持久化输入、输出、缓存读写 Token，历史日志字段为空；
- API Key 管理页面和后端字段需要统一；
- 调用日志需要完整展示实际渠道和计费链路；
- 收入、参考成本和参考利润从消费日志聚合，不能代表供应商真实账单；
- 外部店铺需遵循通用回调协议，具体平台字段仍需适配；
- 邀请奖励的真实触发规则和防刷机制需要核实。

## 11. 当前明确不宣称的功能

以下功能在没有进一步代码证据或实现前，不得对用户宣称已经完成：
