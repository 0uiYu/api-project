# 项目框架与业务模块审计

> 审计目的：在继续二开前，确认现有项目的真实架构、业务调用链、数据来源以及此前修改造成的风险。
> 本文基于当前代码和当前提交 `1c3705741`，不把设计文档中的目标状态当成已实现事实。

## 一、项目定位

当前项目本质上是一个多协议 AI API Relay，不是单纯的模型商城。

它同时包含：

- 用户注册、登录、OAuth、Passkey、二次验证和会话管理；
- API Key/Token 管理；
- 用户组、渠道组、模型能力和渠道选择；
- OpenAI、Claude、Gemini、Responses、Realtime、音频、图片、Embedding、Rerank 等协议中转；
- 钱包额度、订阅额度、充值、兑换码和支付回调；
- 输入、输出、缓存、图片、音频、工具调用等多种计费方式；
- 渠道健康检查、自动禁用、重试、会话亲和性和任务插件；
- 使用日志、审计日志、渠道性能指标和管理后台权限。

因此，前台模型广场不能直接替代后端渠道选择系统。前台展示的是可销售模型和价格，后端真正决定的是某次请求使用哪个渠道、哪个上游模型以及如何结算。

## 二、启动和路由框架

启动入口是 `main.go`。

主要顺序为：

```text
初始化资源
→ 初始化主数据库
→ 初始化权限模型
→ 初始化日志数据库
→ 初始化 Redis/i18n/OAuth
→ 初始化渠道缓存和价格缓存
→ 注册后台任务
→ 注册 Gin 路由
→ 启动 HTTP 服务
```

`router/main.go` 负责组合路由：

- API 路由：`router/api-router.go`；
- Relay 路由：`router/relay-router.go`；
- 管理台和前端静态资源路由；
- 任务插件、视频、Midjourney 等扩展路由。

生产构建使用 `go:embed` 嵌入 `web/dist`。因此只修改前端源码但没有重新构建前端，Docker 中的后端不会自动使用最新前端。

## 三、一次 API 请求的真实过程

```text
客户端携带 API Key
→ TokenAuth 验证 Token
→ 读取 Token 的 group、模型限制、剩余额度
→ 读取用户 group 和用户计费设置
→ Distribute 解析请求模型和协议
→ SelectChannelForRequest 选择渠道
→ SetupContextForSelectedChannel 写入上游 URL、Key、模型映射、Header、参数
→ Relay 根据 RelayFormat 调用对应适配器
→ 上游返回响应和 usage
→ 计算输入/输出/cache/图片/音频/工具调用费用
→ BillingSession 结算钱包或订阅额度
→ 调整 Token 剩余额度
→ RecordConsumeLog 写入消费日志
```

请求是否使用某个渠道，不由前端模型广场决定，也不由渠道名称直接决定，而是由以下因素共同决定：

- 请求模型名；
- Token 的 `Group`；
- 用户的 `Group`；
- 渠道的 `Group`；
- 渠道 `Models` 生成的 `Ability`；
- 渠道状态；
- 渠道优先级和权重；
- 渠道过滤器、任务插件限制、会话亲和性和重试次数；
- 是否指定渠道或渠道被锁定。

## 四、用户、Token、用户组和渠道组

### 4.1 用户组不是展示标签

用户表的 `Group` 会参与后端渠道选择。它不是纯粹的前端分类字段。

Token 也有自己的 `Group`。请求进入 Relay 后，系统通常优先使用 Token 的组作为请求组；`auto` 组还会根据用户组配置多个候选组。

### 4.2 渠道组不是“供应商名称”

`Channel.Name` 是渠道名称，可以写成供应商或线路名称；但 `Channel.Group` 是路由分组，功能不同。

一个渠道记录至少包含：

- 上游类型；
- 上游 Key；
- Base URL；
- 支持模型列表；
- 渠道组；
- 优先级和权重；
- 状态；
- 模型映射；
- 自动封禁设置；
- 上游额外参数和 Header；
- 余额和使用额度。

### 4.3 Ability 是中间索引

渠道保存的是逗号分隔的 `Models` 和 `Group`。系统会把它们展开成 `Ability`：

```text
渠道 A + 模型 claude + 组 default
渠道 A + 模型 claude + 组 vip
渠道 A + 模型 gpt-4o + 组 default
```

渠道更新后需要同步 Ability。Ability 不只是展示数据，它直接影响 `GetRandomSatisfiedChannel` 是否能找到可用渠道。

因此，不能只在前端增加一个“供货商筛选项”，然后认为请求会自动走该供应商。必须明确这个筛选条件最终如何转换成渠道过滤器或 Token 绑定。

## 五、倍率和计费

当前计费不是简单的“模型价格 × 渠道倍率”。实际至少包含：

- `ModelRatio`：模型倍率；
- `GroupRatio`：分组倍率；
- `CompletionRatio`：输出倍率；
- `CacheRatio`：缓存读取倍率；
- `CacheCreationRatio`：缓存写入倍率；
- 图片、音频和工具调用附加价格；
- 自定义价格表达式或按次计费；
- 钱包或订阅作为资金来源；
- Token 自身剩余额度。

文本计费主要在 `service/text_quota.go`，WebSocket、音频等路径在 `service/quota.go`，预扣和结算统一经过 `service/billing.go` 与 `service/billing_session.go`。

预扣流程大致为：

```text
估算本次最大可能费用
→ 预扣 Token 额度
→ 预扣钱包或订阅额度
→ 请求上游
→ 按真实 usage 重新计算
→ 补扣或退款差额
→ 写消费日志
```

所以前台展示的销售价格必须明确是：

- 官方参考价格；
- 用户实际扣费价格；
- 还是某个默认渠道/默认用户组的估算价格。

三者不能混用。

## 六、邀请机制的真实实现

当前注册流程在 `controller/user.go`：

```text
验证邮箱
→ 读取注册请求中的 aff_code
→ 根据 aff_code 查找邀请人
→ 设置新用户 InviterId
→ 插入用户
→ finishInsert
```

`model/user.go` 中的 `finishInsert` 会根据配置处理：

- 被邀请用户奖励 `QuotaForInvitee`；
- 邀请人增加邀请次数；
- 邀请人增加可转余额度 `AffQuota`；
- 邀请历史额度 `AffHistoryQuota`；
- 写入系统日志。

当前邀请机制不是“用户消费后按比例返佣”。它更接近“注册成功时发放固定额度奖励”。如果要实现充值返佣、消费返佣、首充奖励或防刷，需要额外的数据表、结算事件和反作弊规则，当前代码没有完整实现这些业务。

## 七、充值和兑换码

### 7.1 充值

`TopUp` 实际字段是：

- `Amount`；
- `Money`；
- `TradeNo`；
- `PaymentProvider`；
- `Status`；
- 创建和完成时间。

支付回调最终调用不同的 `Recharge*` 函数。成功处理需要：

```text
锁定订单
→ 校验支付渠道
→ 校验订单状态为 pending
→ 计算额度
→ 标记 success
→ 原子增加用户 quota
→ 更新缓存和写日志
```

### 7.2 原有兑换码

`Redemption` 是实际可兑换的单次码。兑换时使用数据库行锁，校验状态和过期时间，然后增加用户额度并把兑换码标记为已使用。

### 7.3 新增店铺订单回调

当前新增的 `/api/redemption/order/webhook` 是自定义协议：

```text
order_id
email
product_name
quota
paid
X-Redemption-Signature
```

处理逻辑是：

```text
验证 HMAC
→ 查找订单
→ 不存在则创建订单和兑换码
→ 根据邮箱尝试绑定用户
→ 发送邮件
→ 标记订单已发放
```

这不是已经确认兼容连动店铺的实现，因为尚未核对连动店铺的真实回调字段、签名方式、重试语义和商品 ID 映射。

## 八、当前确定的问题

### P0：用户摘要充值额度查询字段错误

文件：`model/admin_user_summary.go`

代码查询：

```go
SUM(quota)
```

但 `TopUp` 没有 `quota` 字段，实际充值金额字段是 `Amount` 或 `Money`。该接口在真实数据库中很可能失败，或者无法得到正确的充值统计。

### P0：兑换码订单可能重复发送邮件

订单状态是在发送邮件成功后才更新为 delivered。两个并发回调都可能读取到 pending，然后同时调用 `SendEmail`。订单唯一索引能避免重复创建订单，但不能防止重复发邮件。

需要增加发送中的状态、行锁或发送幂等键。

### P1：订单回调的 `quota` 由外部请求直接决定

当前回调要求外部传入 quota。只要 HMAC 密钥被正确使用，外部系统仍然可以把商品额度传错。更安全的设计应使用 `product_id` 查询本地商品配置，服务端决定额度，而不是信任回调中的 quota。

### P1：渠道状态接口公开

`GET /api/channel-status` 没有管理员认证。需要确认它是否有意对外公开；如果返回渠道名称、余额、上游信息或内部状态，可能造成信息泄露。

### P1：前台价格与真实结算价格没有统一商品定义

`/api/pricing` 返回的是系统动态价格配置和能力信息，不等于“某供应商的销售商品价格”。如果模型广场要展示供应商、用户售价、官方价格、输入输出缓存价格，需要建立稳定的展示 DTO 和价格来源，否则会把内部倍率直接误当成用户价格。

### P1：管理员菜单隐藏不等于后端禁止访问

前端侧边栏只是显示控制。真实权限仍然由 `AdminAuth`、`RootAuth` 和 Casbin 权限决定。任何“管理员不应该看到”的页面，都必须同时检查路由权限和 API 权限。

## 九、下一步修改顺序

1. 先修复并测试用户摘要字段，明确充值统计口径：充值金额、实际到账额度、成功订单数必须分开。
2. 核对连动店铺的真实回调协议，再设计商品映射和幂等发码流程。
3. 明确模型广场 DTO：供应商、模型、官方价格、用户价格、输入、输出、缓存读、缓存写、渠道状态分别来自哪里。
4. 明确“用户选择渠道”到底是 Token 固定绑定、请求级渠道过滤，还是只做前台展示；三种方案不能混用。
5. 完成渠道、Ability、用户组、Token 组到实际请求的集成测试。
6. 完成钱包、Token、订阅的预扣/结算/退款测试，再修改计费页面。
7. 最后再调整管理台菜单和页面，避免前端展示先于后端业务定义。

## 十、阶段 3 核对结果：API Key 选择的是分组，不是供应商

当前 Token 模型只有 `Group`、`AutoGroups` 和模型限制等字段，没有供应商或单渠道绑定字段。

请求中实际使用的组由以下逻辑决定：

```text
Token.Group
→ auto 时读取 Token.AutoGroups 或全局 Auto 顺序
→ 校验这些组是否是用户可选组
→ 根据组 + 请求模型查 Ability
→ 在满足状态、优先级、权重和过滤器的渠道中选择
```

因此当前前端 API Key 弹窗中的“分组”选项是有后端意义的；它不是简单的展示字段。把它直接改名为“供应商”是不正确的，因为一个分组可以包含多个供应商渠道，后端还会在这些渠道之间进行选择和重试。

如果业务确实要求用户固定选择某一家供应商，需要新增明确的 Token 渠道约束，例如 `channel_id` 或安全的 `channel_tag`，并让 `SelectChannelForRequest` 强制应用该约束。仅修改前端下拉框不会改变实际请求路由，也不能实现供应商固定绑定。

当前阶段结论：保留现有分组路由模型，不新增未经确认的供应商绑定字段；模型广场中的供应商筛选必须作为展示/筛选维度单独设计，不能直接复用 Token.Group。

## 十一、阶段 4 核对结果：`/api/pricing` 不是供应商商品价格表

当前 `/api/pricing` 返回的 `Pricing` 包含：

- 模型名称、图标、描述和供应商 ID；
- 官方输入、输出、缓存读取、缓存写入参考价格；
- 模型倍率、输出倍率、缓存倍率；
- 可用分组；
- 计费模式和动态计费表达式；
- 支持的端点类型。

其中：

- `Official*Price` 是官方参考价格，用于成本估算和前台参考；
- `ModelRatio`、`CompletionRatio`、`CacheRatio` 等是系统结算配置；
- `EnableGroup` 是访问范围，不是供应商；
- `VendorID` 是模型元数据供应商，不等于实际本次请求命中的渠道；
- 当前结构没有“每个供应商/每条渠道的独立销售价格”字段。

因此模型广场可以安全展示：模型、图标、官方参考价格、当前用户可用分组及系统计费倍率；但不能在没有新业务定义的情况下声称展示了某个供应商的真实售价或真实成本。

如果需要真正实现“供应商 + 模型 + 平台售价”的商品目录，建议新增独立的目录层，不修改现有 `Pricing` 语义：

```text
catalog_model
catalog_provider
catalog_offer
```

`catalog_offer` 至少需要保存模型、展示供应商、可用渠道约束、用户价格、输入价格、输出价格、缓存读写价格、状态和更新时间。请求结算时仍必须使用后端真实计费配置，不能只依赖前台目录价格。
