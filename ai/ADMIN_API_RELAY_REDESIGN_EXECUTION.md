# API 中转站管理端重构执行任务

## 任务身份

你是当前项目的实施 AI。你的目标是把现有项目的管理端整理并改造成真正可运营的 API 中转站管理台。

用户端已经完成基础改造，本任务重点只处理管理端、后端管理能力和与中转业务直接相关的统计、权限及流程。

## 强制执行规则

1. 必须先完整阅读项目，再修改代码。
2. 必须优先阅读 `AGENTS.md`、`CLAUDE.md`、项目规则文件及本任务文件。
3. 必须检查后端 `router`、`controller`、`service`、`model`、`relay`、`middleware`、`setting`，以及前端 `web/src/routes`、`web/src/features`、权限和侧边栏实现。
4. 不得凭项目名称、旧项目经验或前端页面猜测业务。所有结论必须来自代码、数据库模型、接口和实际调用链。
5. 不得只修改前端显示来伪造业务完成。涉及计费、路由、权限、兑换码、订单、统计的功能，必须检查并实现真实后端逻辑。
6. 不得修改已经完成的用户端功能，除非管理端改造确实需要共享接口或权限修复。
7. 不得删除无关代码，不得重置用户已有修改，不得执行破坏性 Git 操作。
8. 所有密钥、Authorization、API Key、用户隐私内容必须脱敏。
9. 发生不确定事项时，先在代码中核查；无法确认时明确记录为阻塞，不得编造结论。
10. 除非遇到无法继续的外部阻塞，否则不要中途向用户汇报。
11. 必须执行完本文件所有阶段后，才进行最终汇报。
12. 最终汇报必须包含：完成项、修改文件、数据库变化、接口变化、验证结果、未完成项和真实阻塞原因。

## 中途汇报规则

不要按阶段主动汇报进度。

只有以下情况可以暂停并汇报：

- 缺少用户必须提供的密钥、第三方接口凭证或外部服务权限；
- 数据库迁移会造成不可逆数据破坏，且无法安全兼容；
- 当前代码存在无法绕过的编译或环境阻塞，并且已经完成合理排查；
- 用户要求暂停。

普通的代码复杂、测试失败、旧代码质量差、需要多次修改，都不是暂停理由，应继续处理。

## 目标业务模型

系统的核心链路必须保持清晰：

```text
上游渠道
→ 渠道支持的模型
→ 模型映射和价格配置
→ 用户创建 API Key
→ 用户调用 API
→ API Key 鉴权
→ 确定用户分组和计费规则
→ 查找可用渠道
→ 根据状态、优先级、权重选择渠道
→ 转换请求协议和模型名称
→ 请求上游
→ 解析响应和 Token
→ 结算用户扣费
→ 记录用户、模型、渠道、Token、费用和延迟
```

必须区分以下概念：

- `Channel`：实际向上游发送请求的渠道配置。
- `Provider`：供货商展示或归类信息，不得默认当成实际请求对象。
- `Model`：用户请求的模型或系统管理的模型记录。
- `Model Mapping`：用户模型名称到上游模型名称的映射。
- `User Group`：用户侧权限、价格或路由规则。
- `Channel Group`：渠道能够承接的请求分组。
- `API Key`：用户访问中转 API 的凭证。
- `Quota`：系统内部额度单位。
- `User Charge`：用户实际被扣除的额度或金额。
- `Upstream Cost`：上游真实成本或管理员维护的成本价格。
- `Profit`：用户收入减去上游成本。

如果当前项目对其中某个概念的实现不同，必须以实际代码为准，并在最终报告中说明。

## 阶段一：完整审计

先不要修改代码，完成以下只读审计：

### 后端

- 启动方式和环境变量。
- 主路由和认证中间件。
- 管理员权限判断。
- API Key 鉴权流程。
- 渠道模型和渠道选择流程。
- 模型、模型映射和倍率配置。
- 计费、预扣、结算、退款流程。
- 调用日志和统计数据来源。
- 兑换码、充值、订阅和支付回调。
- 邀请关系和奖励逻辑。

### 前端

- 管理端所有路由。
- 用户端所有路由。
- 侧边栏、权限过滤和角色判断。
- 渠道页面、模型页面、用户页面、Key 页面、日志页面。
- Dashboard 和模型调用分析页面真实读取的接口及字段。
- 当前用户端已有的改造，不得误改。

### 审计输出要求

把审计结果写入：

```text
ai/ADMIN_API_RELAY_AUDIT.md
```

内容至少包括：

- 当前架构图；
- 核心数据库表和字段；
- API 请求完整链路；
- 管理端当前功能；
- 用户端当前功能；

- 计划修改的文件和原因。

## 阶段二：管理员导航和权限

管理员主菜单整理为：

```text
管理台
├── 运营概览
├── 渠道管理
├── 渠道状态
├── 模型管理
├── 价格与倍率
├── 用户管理
├── API Key 管理
├── 调用日志
├── 兑换码管理
├── 订单与订阅
├── 收入成本分析
├── 审计日志
└── 系统设置
```

要求：

- 管理员不显示模型广场、用户聊天、用户 Playground、个人资料、个人充值、个人邀请、个人安全设置。
- 普通用户不显示管理端菜单。
- 普通管理员和超级管理员按照后端权限区分。
- 仅隐藏菜单不算完成，后端接口也必须验证权限。
- 直接访问管理路由、手动修改请求参数、调用管理 API 都不能绕过权限。
- 不存在的页面不能添加到菜单；如功能缺失，先实现页面或明确记录未实现。

## 阶段三：渠道管理和渠道状态

渠道列表必须支持展示：

- 渠道名称；
- 供货商名称；
- 协议类型；
- 支持模型数量；
- 分组；
- 状态；
- 优先级；
- 权重；
- 响应时间；
- 成功率；
- 今日请求数；
- 最后测试时间；
- 最近错误。

渠道编辑必须检查并支持：

- Base URL；
- API Key；
- 支持模型；
- 模型映射；
- 分组；
- 优先级；
- 权重；
- 启用/禁用；
- 超时和重试；
- 请求头覆盖；
- 参数覆盖；
- 测试模型。

要求：

- 列表和普通接口不能返回完整密钥。
- 编辑渠道时未提交密钥不能清空原密钥。
- 渠道状态页面必须读取真实状态，而不是只维护一个前端假状态。
- 支持测试渠道和测试指定模型。
- 手动禁用、自动禁用和启用状态必须在路由选择中生效。

- 创建缓存价格；
- 是否展示；
- 是否可用；
- 备注。

```text
用户请求模型 → 上游真实模型
```

价格页面必须明确区分：

- 用户价格；
- 上游成本或参考价格；
- 用户组倍率；
- 渠道倍率；
- 输入倍率；

- 缓存读取倍率；
- 缓存创建倍率；
- 最终用户扣费；
- 上游成本；
- 利润。

不得在后端不支持时只增加前端字段。

如果历史账单没有价格快照，必须评估是否补充快照字段，确保未来修改价格后不会改变历史数据。

## 阶段六：调用日志和模型调用分析

调用日志筛选至少支持：

- 用户；
- 用户组；
- API Key；
- 模型；
- 渠道；
- 请求状态；
- 时间范围；
- Request ID；
- 上游 Request ID。

详情必须能够追踪：

```text
用户请求
→ API Key 鉴权
→ 用户组确定
→ 候选渠道
→ 实际渠道
→ 模型映射
→ 上游请求
→ Token 解析
→ 用户扣费
→ 成本计算
→ 日志落库
```

模型调用分析必须明确标识：

- 总调用次数；
- 用户侧扣费额度；
- 总 Token；
- 平均每分钟请求数；
- 平均每分钟 Token 数；
- 成功率；
- 平均延迟；
- 吞吐量。

必须核实当前项目是否独立保存：

- 输入 Token；
- 输出 Token；
- 缓存读取 Token；
- 缓存创建 Token。

如果没有，不能在页面伪造这些数据，应明确显示当前只能统计总 Token，并评估数据库和日志改造。

不得把用户扣费直接命名为上游成本、收入或利润。

## 阶段七：运营统计、成本和利润

运营概览至少支持：

- 请求量；
- 成功请求量；
- 失败请求量；
- Token 使用量；
- 用户扣费；
- 上游成本；
- 利润；
- 活跃用户；
- 启用渠道；
- 异常渠道。

如果当前没有上游成本数据：

- 不得用用户扣费代替成本；
- 不得伪造利润；
- 先补充成本计算和持久化；
- 推荐在结算时保存价格快照。

建议保存：

```text
input_cost
output_cost
cache_read_cost
cache_write_cost
total_upstream_cost
user_charge
profit
```

## 阶段八：兑换码、订单和邀请

先核实现有兑换码机制，不得假设外部店铺已经集成。

外部店铺回调流程必须具备：

```text
付款成功
→ 店铺回调
→ 签名校验
→ 订单幂等校验
→ 生成或分配兑换码
→ 发货或邮件发送
→ 记录发送结果
→ 用户兑换
```

必须防止：

- 重复回调重复发货；
- 同一兑换码重复兑换；
- 伪造回调；
- 发货失败无法重试；
- 订单和兑换码无法关联。

邀请机制必须明确真实奖励触发条件：

- 注册奖励；
- 充值奖励；
- 消费返佣；
- 奖励额度；
- 奖励上限；
- 防刷规则。

没有实现的奖励类型不得在管理端宣称已支持。

## 阶段九：验证要求

每完成一个模块都必须运行适用的验证：

- 前端类型检查；
- 前端相关测试；
- 后端单元测试；
- 后端相关测试；
- 数据库迁移检查；
- 路由和权限检查；
- `git diff --check`。

至少覆盖以下场景：

- 普通用户访问管理 API 被拒绝；
- 管理员不能读取明文渠道密钥；
- 禁用渠道不会被路由选中；
- 模型映射正确生效；
- 用户扣费正确；
- 失败请求不重复扣费；
- API Key 过期或禁用后不能调用；
- 兑换码不能重复兑换；
- 外部订单重复回调不会重复发货；
- 价格调整不会修改历史统计。
